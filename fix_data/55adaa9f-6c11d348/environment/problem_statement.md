# Add semantic runtime transforms for Specta types

Specta describes Rust data accurately in TypeScript, but values decoded from JSON still use their wire representation. Add a `specta-tags` workspace crate that identifies values needing runtime conversion and supplies JavaScript or TypeScript that turns large integers into `BigInt`, date-like strings into `Date`, and byte arrays into `Uint8Array`.

The crate has two public integration surfaces whose names are part of its compatibility contract. The root surface exposes `Analyzer`, `SemanticKind`, `TransformSpec`, `EnumVariantTransformSpec`, `EnumVariantTransformKind`, `RuntimeRequirements`, `RuntimeTarget`, and `render_runtime`. `Analyzer::with_builtins()` enables the standard mappings, `with_named_type` adds a mapping selected by both module path and type name, and `with_list_u8_is_bytes` controls whether `List<u8>` is treated as bytes. Analysis must cover primitive, named, generic, nullable, list, tuple, object, map, enum, and recursive type graphs without recursing forever.

`TransformSpec::to_json` is a public compact protocol. Identity, bigint, date, and bytes are encoded as `0`, `1`, `2`, and `3`. Nullable, list, tuple, object, map, and enum specs are encoded as `[4, inner]`, `[5, inner]`, `[6, items]`, `[7, fields]`, `[8, inner]`, and `[9, variants]`. Object entries are `[name, spec]`. Enum entries are `[name, kind, spec]`, with kind codes `0`, `1`, and `2` for unit, named, and unnamed variants.

`RuntimeRequirements::from_specs` determines which conversions a runtime needs. With no requirements, `render_runtime` returns an empty string. Otherwise its JavaScript output must execute as JavaScript and its TypeScript output must compile and perform the same requested conversions. Conversions not requested by the requirements remain inactive. Malformed primitive or container values passed to an active runtime are returned unchanged rather than causing an exception.

`with_result_helper(true)` additionally reserves a promise-result adapter, including when no other conversion was requested. It accepts promises resolving to either `{ status: "ok", data: T }` or `{ status: "error", error: E }`, applies the supplied transform spec to `data` or `error`, and preserves the corresponding envelope. The runtime's public reserved identifiers are `__TS_transform`, `__TS_transformEnum`, and `__TS_transformResult`, exposed through `RUNTIME_RESERVED_NAMES`.

The second surface is `v2::TransformPlan`: `TransformPlan::analyze(DataType, &Types)` builds a reusable plan and `map(input)` returns a JavaScript expression for any caller-supplied input expression. It must transform the same leaf values through nested structs, generic and named references, nullable values, lists, tuples, maps, recursive graphs, and externally, internally, and adjacently tagged enums. It must preserve fields and collection keys that do not need conversion. Untagged enums remain unchanged because their variants have no discriminator, and an identity-only graph returns the caller's exact input expression.

The built-in date mappings are `std::time::SystemTime`, `toml::value::Datetime`, `chrono::{NaiveDateTime, NaiveDate, Date, DateTime}`, `time::{PrimitiveDateTime, OffsetDateTime, Date}`, `jiff::{Timestamp, Zoned}`, `jiff::civil::{Date, DateTime}`, and `bson::DateTime`. The byte mappings are `bytes::{Bytes, BytesMut}`. A short type name in any other module must not activate a built-in mapping.

Integrate the crate as a workspace member and include development support for derived Specta types and the `chrono` and `bytes` values used by the examples.
