Story-view navigation in the crit web UI (`web/app.js`, `web/crit-renderer.js`) jumps to the wrong place when you click a comment or an anchor. The Story view splits a diff into chapters, and clicking a comment is supposed to activate the chapter that owns the matched line and scroll to it. Right now the line→hunk lookup ignores which side of the diff (old vs new) the coordinate belongs to, so it just scans every hunk for any line whose `OldNum` OR `NewNum` equals the target and takes the first hit. That's wrong: a net deletion shifts later `NewNum`s down onto an earlier hunk's `OldNum`, and an old-side deletion can collide with some unrelated `NewNum`, so navigation lands in the wrong chapter. It also breaks after adjacent hunks get visually merged (small-gap auto-expansion and comment-gap expansion), because the merged hunk loses track of which raw hunk each line originally belonged to. On top of that, file-scoped comments navigate using a fake line number, scope/base/commit reloads leave stale Story clones around, and unified-vs-split diff rows aren't translated correctly when scrolling to the target.

What needs to hold:

Comment anchors need to carry side and scope. In `web/crit-renderer.js`, the anchor returned by `anchorFromComment(comment)` must include `comment.scope` alongside its existing fields. For a line-scoped comment such as `{ file_path: 'a.go', start_line: 1, end_line: 5, side: 'old', scope: 'line' }`, the resulting anchor has `type: 'line'`, `filePath: 'a.go'`, `startLine: 1`, `endLine: 5`, `side: 'old'`, `scope: 'line'`. For a file-scoped comment such as `{ file_path: 'a.go', start_line: 0, end_line: 0, scope: 'file' }`, the anchor has `type: 'line'`, `filePath: 'a.go'`, `scope: 'file'`, and `side` remains `undefined` — file scope carries no side.

A side-aware raw-hunk lookup `storyRawHunkForLine(hunks, line, side)` returns the matching candidate as `{ hunk, rawHunk }`, or `null` when there is no match. The search respects the coordinate space: when `side === 'old'`, matches occur only against `OldNum`; when `side === 'new'` (or `side === ''`), matches occur only against `NewNum`; when `side` is omitted, `undefined`, or `null`, the legacy fallback applies, trying `NewNum` first across all hunks, then `OldNum`. Given a deletion hunk at `OldStart: 7` and a later add hunk at `OldStart: 24`, a lookup of line 17 on the `new` side resolves to the `OldStart: 24` hunk, while the same line 17 on the `old` side resolves to the `OldStart: 7` hunk. A side-less lookup of 17 preserves new-then-old ordering and resolves to the `OldStart: 24` hunk. A pure deletion (`del` at `OldStart: 30`, line 31) looked up on the `old` side resolves to that hunk. An insertion mapping (`add` line 22) on the `new` side resolves to its own hunk.

3. Preserve raw-hunk ownership across merges. When adjacent hunks are combined — both the automatic small-gap merge in `autoExpandSmallGaps(file)` and the comment-driven merge in `expandHunksForComments(file)` — the merged visual hunk must remember the original raw hunks so `storyRawHunkForLine` still resolves each line to its true owner (identified by the raw hunk's `OldStart`). Context lines synthesized in the gap between two hunks belong to the preceding raw hunk. Concretely: after merging a hunk at `OldStart: 7` (containing a deletion of old line 17) with a later hunk at `OldStart: 24` (containing an add of new line 17), `file.diffHunks` collapses to length 1, but `storyRawHunkForLine(file.diffHunks, 17, 'new').rawHunk.OldStart` is 24 and `storyRawHunkForLine(file.diffHunks, 17, 'old').rawHunk.OldStart` is 7. For comment-gap expansion where a comment forces a synthesized context line at new line 15 between a hunk at `OldStart: 10` and one at `OldStart: 20`, the merged hunk collapses to length 1 and `storyRawHunkForLine(..., 15, 'new').rawHunk.OldStart` must be 10 (the synthesized gap context belongs to the preceding raw hunk), while `storyRawHunkForLine(..., 21, 'new').rawHunk.OldStart` is 20. Same for automatic small-gap expansion: a synthesized line 13 resolves to the preceding raw hunk `OldStart: 10`, and later line 16 resolves to `OldStart: 15`.

4. Add `storyDisplayAnchorForLine(hunks, line, side, mode)` to translate a route coordinate into the row identity the active renderer uses. Ownership stays in the anchor's true old/new space; only unified context rows need translating because they render once using the new-side row. Given a hunk with context (old 24/new 14), a deletion (old 25), an add (new 15) and context (old 26/new 16):
   - unified + old-side context (line 24) → `{ line: 14, side: '' }` (maps to its single new-side context row)
   - unified + old-side deletion (line 25) → `{ line: 25, side: 'old' }` (keeps the deleted row)
   - unified + new-side addition (line 15) → `{ line: 15, side: '' }`
   - unified + new-side context (line 16) → `{ line: 16, side: '' }`
   - split + old-side context (line 24) → `{ line: 24, side: 'old' }` (keeps its distinct left-side row)
   For a side-less legacy call, follow whichever coordinate side actually matched: `storyDisplayAnchorForLine([deletionHunk], 17, undefined, 'unified')` where the hunk only has old line 17 must return `{ line: 17, side: 'old' }`.

5. File-level navigation. Add `storyPageForFile(filePath)` returning the id of the first chapter that references the file (or null), and `storyActivatePageForFile(filePath)` which activates that chapter and returns `true` if navigation happened, `false` otherwise. `storyPageForLine(filePath, line, side)` / `storyActivatePageForLine(filePath, line, side)` must take the side through to `storyRawHunkForLine`. Given story state with pages `chapter-1`, `chapter-2` and `fileChapters` mapping `src/a.go` to the chapter-2 index, `storyPageForFile('src/a.go')` returns `chapter-2`, `storyActivatePageForFile('src/a.go')` returns `true` and makes `chapter-2` the shown chapter, and `storyActivatePageForFile('missing.go')` returns `false`. Only the side-less/legacy `storyPageForLine` path may fall back to the file-level owner; an explicit-side miss must return `null` rather than jumping to an unrelated chapter.

In `web/app.js`, the production Story callers must carry side and display mapping through scroll routing. Comment-card navigation resolves through `storyActivatePageForLine(filePath, line, side)` with the comment's side preserved. File-scoped comments navigate by file ownership rather than a synthetic line, following `fileScope ? storyActivatePageForFile(filePath) : ...`. Renderer anchor navigation resolves through `storyActivatePageForLine(anchor.filePath, anchor.endLine, side)`, and renderer scrolling translates route coordinates via `storyDisplayAnchorForLine(file.diffHunks, anchor.endLine, side, diffMode)`. The Story scroll target selector reflects the translated side, built as `data-diff-side="` + `displayAnchor.side`. Renderer file anchors (`anchor.scope === 'file'`) resolve through the file-level Story navigation path.

7. Scope reloads must not reuse stale Story clones. `async function reloadForScope()` keys cached Story clones by the final file-content hash, but a scope/base/commit change can swap the diff hunks without changing that hash. When a scope reload occurs, `storyExpandedFileCache` must be invalidated before `loadAllFileData` runs, so that replacement data is not matched against stale clones.

The embedded `web/markdown-it.min.js` and `web/mermaid.min.js` vendor bundles are aligned to match the versions crit-web uses, though the navigation behavior described above is what matters for correctness.

Do not modify any test files. The existing renderer contract (`register` requiring the six renderer methods, DOM anchors, etc.) must keep working unchanged.
