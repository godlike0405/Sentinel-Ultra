sif currently scans a list of targets one at a time, so elapsed time grows with the list even though most target scans are independent and waiting on network I/O. Add opt-in target-level parallelism with a `-concurrency` flag. Its default is 1, and zero or negative values must behave as 1 rather than stalling or panicking.

When the effective concurrency is greater than 1, no more than the requested number of target scans may run at once, and concurrency must not exceed the number of targets. Keep every target's scan state isolated. Completion timing must not affect the run-wide result: API records, findings, report sections, scan labels, and log-file summaries must retain target input order and contain each target's data exactly once.

When target scans run in parallel, errors that abort a target's processing must be surfaced as the run-level error. Once a fatal target failure is observed, do not begin further queued targets, but allow target scans that already began to finish before the run returns. If more than one of those scans fails, the run-level error must identify every failed target and its underlying failure exactly once, in target input order rather than completion order. Preserve the existing best-effort behavior of scanner stages that log an error and continue. Panics in parallel target workers must follow the same fatal-error behavior.

In the parallel path, a fatal target failure must not discard work from targets that completed successfully, including work finished by an already-running target while the failure was being drained. Those successful targets must still contribute their API records, findings, report sections, scan labels, and log-file summaries exactly once in input order; failed and never-started targets must not contribute partial run-wide records. Run-wide finalization must still be attempted, and a finalization failure must be returned alongside target failures rather than masking them.

Parallel scans share the console. Console output produced by simultaneous target scans must remain readable: one target's output must not be corrupted or overwritten by another's. This guarantee also applies when independent parallel runs overlap in the same process; completion or failure of one run must not disrupt output safety for another run that is still active. Once all parallel runs have ended, later sequential runs must retain their normal live output, including after a parallel failure.

Leaving `-concurrency` unset, explicitly setting it to 1, or passing a non-positive value must preserve today's sequential behavior, including result order and live output. The parallel path must be race-safe and pass under `go test -race`.

An `App` may be run again after either success or failure, and its effective concurrency may change between invocations. Every invocation must have fresh run-wide bookkeeping: summaries and exported results may contain only that invocation's target work, and a failed parallel invocation must not poison a later sequential or parallel run.
