Pouch currently asks containerd to build the initial OCI specification for every new container, even though the result mostly represents Pouch policy and is immediately adjusted by later setup. Move ownership of that default Linux profile into Pouch so ordinary container creation no longer depends on containerd to supply it.

Keep the resulting container behavior compatible with what Pouch already expects. Ordinary containers should start with the existing capability sets, Linux namespaces, protected proc paths, mount security settings, and device permissions. The profile should deny device access by default, allow null, zero, random, urandom, tty, and console, and preserve the FUSE denial.

There are a few intentional differences from containerd's profile. `/run` should not be included, while the cgroup mount should be present and read-only for ordinary containers. `/dev/shm` should default to 64 MiB, but `/dev` itself should not carry that size limit. `/proc` must use `nosuid`, `noexec`, and `nodev`. The obsolete `/sys/firmware` and `/proc/scsi` masks should not be carried forward.

Container-specific settings still take precedence over these defaults. A configured positive shared-memory size must be the sole effective size on the final `/dev/shm` mount; an omitted or zero value keeps the 64 MiB default. A user bind mount at `/dev/shm` should remain a bind mount with the requested access and propagation behavior, without inheriting tmpfs sizing. Privileged containers keep writable `/sys` and cgroup mounts and do not retain the ordinary protected paths.

Creating or modifying one container must not alter the defaults or final specification of another. Cgroup paths should continue to be normalized from the configured parent and container ID, and the normal container creation path must use the Pouch-owned profile without requiring containerd to generate a starting specification.

The completed OCI specification should also be an owned snapshot of the container settings used to build it. Later changes to a container's command arguments, environment, sysctl settings, or resource limits must not rewrite an already-built specification, and editing those values in the specification must not change the stored container configuration. This must hold for values the specification reaches through pointers as well as through slices and maps, and building the specification must not write into spare capacity that a container's own storage still owns. Capability additions and removals must be reflected consistently in all four OCI capability sets, while each set remains independently editable after finalization. Building a second specification for the same container must leave an earlier completed specification unchanged. These isolation guarantees must continue to hold when specifications for multiple containers are created concurrently.

Specification publication must be transactional. If validation fails at any stage — including process, mount, plugin hook, and platform-specific validation such as device and block-IO settings — creation should return an error rather than panic, must not expose a partial specification, and must leave any previously completed specification in the same wrapper untouched. A rejected attempt must also leave the container itself exactly as it was, including any container state that setup would otherwise record along the way, and must not disturb the plugin hook input it was given. Correcting the rejected settings and retrying with that wrapper should then publish a complete profile normally. When a specification is published successfully, container state that the setup stages resolve — such as the paths of the network files a container ends up using, whether they came from its existing configuration or from user mounts that replace them — must be recorded on the container, leaving unrelated paths alone. Pre-start hook commands supplied by plugins are part of the same snapshot contract: the completed specification and the plugin's argument arrays must remain independent in both directions, and malformed hook command/priority input must fail without disturbing an earlier successful profile. Concurrent creations that mix valid and rejected containers must each get their own outcome without affecting the others.
