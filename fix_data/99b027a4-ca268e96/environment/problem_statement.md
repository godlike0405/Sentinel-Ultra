**Summary.** The whale agent can launch shell commands as long-lived background tasks, and users manage them from the TUI with two slash commands: `/ps` to list background shell tasks and `/stop` to terminate one. Today `/stop` only stops a single task at a time — it requires a `task_id` argument (`/stop <task_id>`), so a user who has started several background jobs must copy each opaque task identifier out of `/ps` and issue `/stop` once per job to clear them. There is no way to stop everything at once, and the listing output forces users to read and shuttle around machine-generated IDs that carry no meaning to them.

**User story.** As a user with one or more running background shell tasks, I want to type `/stop` with no arguments and have every currently-running background task terminated in a single action, and I want the task listings to identify jobs by the command they are running rather than by an internal task ID.

**Acceptance criteria.** The `/stop` command must take no arguments and stop all running background shell tasks. Invoking `/stop` with no argument is the valid form; invoking `/stop <task_id>` (or `/stop` with any extra token) must now be rejected as a usage error whose message contains `usage: /stop`. When `/stop` runs and there are no running tasks, it must succeed (not error) and report `No background shell tasks running.`. When it stops tasks, the result text must begin with a count line: exactly `Stopped 1 background shell task.` when one task was stopped, and `Stopped N background shell tasks.` (e.g. `Stopped 2 background shell tasks.`) when N>1 tasks were stopped. Each stopped task must then be described by its command string, its status, and its working directory (`cwd:`) when known — and must not include the internal task ID anywhere in the output. After `/stop` completes, no previously-running task may still be in the `running` state.

The `/stop` command is a local, state-mutating command that must remain available and dispatch immediately even while the agent is busy. It classifies as local-mutating when given no arguments, and as a usage error otherwise. In the slash-command catalog it must be described as `Stop all background shell tasks` and marked as auto-run (it takes no argument hint). In the TUI, selecting the `/stop` suggestion and pressing Enter must auto-run it immediately: it dispatches exactly one local-submit intent whose input is `/stop`, and clears the input box (it must not wait for a task-id argument or leave a trailing space). The help listing must show the command as `/stop` (no `<task_id>` argument hint).

**Listing behavior (`/ps`).** `/ps` must list only tasks that are currently running. Tasks that have been canceled, or that have finished by timing out (status `timeout`), must not appear in the `/ps` output — neither their command nor any identifier. Running tasks must be shown by their command text (e.g. `sleep 30`), not by their task ID, and must be ordered by start time (earliest first). When no tasks are running, `/ps` must emit `No background shell tasks running.`; in that empty state the command's structured local result must contain exactly one field whose label is `running` and whose value is `none`. Immediately after a `/stop` clears everything, `/ps` must report the running-empty state and must not show any of the just-canceled commands.

**Underlying task-management requirements.** `Toolset.RunningBackgroundShellTasks()` must enumerate only running background shell tasks, distinct from `Toolset.BackgroundShellTasks()`: the running-only view must exclude canceled and timed-out tasks, while the full view must retain the complete task history (a canceled or timed-out task still appears in the full history with its final status). `Toolset.CancelAllBackgroundShellTasks(context.Context)` must cancel every currently-running background shell task, wait briefly for each to terminate, and return the stopped tasks ordered by start time. The stop-all operation must be idempotent: calling it again when nothing is running returns an empty result with no error, and after it runs there must be no tasks left in the `running` state. `Toolset.CancelBackgroundShellTask(context.Context, taskID)` must continue to cancel one task by ID; a canceled task leaves the running view but remains in the full history.

**TUI shell result summaries.** When a `shell_run` tool result reports a command still running in the background, the chat summary must no longer append the task ID. The running summary must read `running · <duration>` (e.g. `running · 15s`) with no task-id suffix, and when a diagnosis reason is present it must read `<reason> · <duration>` (e.g. `build/test running · 15s`) — again with no task-id suffix.
