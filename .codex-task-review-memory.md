# Sentinel-Ultra task review memory

Apply this checklist whenever creating or modifying a task in this workspace.

## Mandatory post-fix learning loop

- After fixing any task error, record the generally applicable cause,
  prevention check, validation command or evidence, and any relevant
  clean-base/oracle/NOP regression check in this file.
- Record lessons from manual review, local execution, platform evaluation,
  automated judges, agent rollouts, packaging failures, and reviewer feedback.
- Keep entries concise and reusable; do not store task-specific secrets,
  solution code, hidden-test answers, or identifiers unless the identifier is
  necessary to explain a general collision pattern.
- Never weaken or delete earlier checks when adding a new lesson. If a new
  lesson refines an older one, preserve the stronger combined requirement and
  note any real platform/version condition that determines which behavior
  applies.
- Reapply the new check to the task just fixed and to every future task created,
  reviewed, modified, fixed, validated, or packaged in this workspace.

## Mandatory Agentic Judge gate

- Assess all ten axes for every created or modified task: `clarity`,
  `oracle_no_gaming`, `oracle_reproducibility`,
  `oracle_spec_faithfulness`, `packaging`, `prescriptiveness`, `realism`,
  `self_containedness`, `test_coverage`, and `test_faithfulness`.
- Require every axis to score at least **3.5/5** before treating the task as
  ready. Revise any axis below 3.5 and repeat the full affected audit.
- When platform judge output is available, report its actual per-axis scores
  and justifications. Otherwise label scores as internal preflight estimates;
  never present an estimate as an executed platform result.
- Treat the minimum individual judge concern as actionable: a low coverage or
  faithfulness assessment cannot be hidden by averaging it with a higher score.
- Maintain a per-axis evidence table citing exact instruction requirements,
  tests, oracle behavior, metadata/package artifacts, and executed validation.

## Form-answer writing and copyability

- Write every step-by-step form answer in natural, task-specific language.
  Avoid generic rubric recitations, robotic parallelism, academic filler,
  repetitive conclusions, or phrasing that merely mirrors the question.
- Ground each answer in concrete evidence from the current bundle: exact files,
  requirements, test IDs, configuration values, commands, or observed results.
- Present each required form field separately, with its question/field label and
  one self-contained answer that can be copied without editing neighboring
  fields.
- Wrap long prose into short readable paragraphs or lines; do not produce a
  single dense wall of text or combine multiple form fields into one block.
- Use checkboxes or selected-option labels for choice fields and plain prose for
  text fields. Use `NA` only when the field genuinely does not apply.
- Keep the human-review integrity warning: the EC must independently verify and
  take responsibility for submitted reviewer prose rather than pasting a draft
  without review.

## Agentic Judge lesson: executable presence is not behavioral coverage

- Define every observable success contract precisely. Do not use phrases such
  as deterministic validation, graceful handling, readiness, or drift
  detection without specifying the externally observable result, baseline,
  exit/status behavior, and relevant unsupported-case semantics.
- Make tests induce and detect the promised behavior. Building a named target,
  registering it, running it twice, and observing exit zero does not prove that
  it performs the required numerical, security, compatibility, or validation
  work.
- Add a negative/control scenario showing that a stub executable or no-op
  implementation fails. If an empty implementation returning success can pass,
  test coverage is insufficient.
- Exercise every promised operation, precision, runtime mode, architecture, and
  unsupported-path behavior independently when each is part of the contract;
  do not rely on transitive execution or target-name existence as proof.
- When the task promises deterministic drift detection, use verifier-owned
  controlled inputs/baselines and deliberately altered results to prove that
  unchanged results pass and drift fails, without exposing hidden answers or
  prescribing the implementation.

## Harbor configuration

- Do not add `network_mode`, `allowed_hosts`, or other egress-control declarations speculatively. Preserve them when the seed or current platform contract requires them; otherwise they can unnecessarily activate Harbor's egress sidecar and fail on hosts whose Docker frontend does not support the required buildx flags.
- Do not apply the older blanket-removal rule when the current task schema or target platform explicitly requires `network_mode` and `allowed_hosts`; preserve required settings and validate them against the actual installation rather than changing them speculatively.
- Distinguish image construction from verification: build-time dependency downloads can be acceptable when the target platform permits them, but the completed verifier must run without network access or live services.
- Treat an unset `EGRESS_CONTROL_SIDECAR_IMAGE_NAME` during Compose cleanup as a likely cascade from a failed sidecar build.
- Treat `SandboxBuildFailedError` and oracle `0/N valid trials` as an environment failure, not agent or difficulty evidence. No trial started, so fix and validate the image before interpreting rollout results.
- Before submission, build `environment/Dockerfile` from a fresh checkout with a cold cache and inspect the first failing layer. Verify the concrete base tag, distribution repositories, package availability, copied paths, shell commands, and executable bits.
- Minimize build-time package sources and remove avoidable live dependency resolution. Old pinned images can still exist while their distribution repositories have expired; image-tag availability alone is not a successful build check.
- If Docker is unavailable locally, say so explicitly. Registry metadata inspection or extracted-rootfs testing can diagnose likely failures but must not be reported as a completed Docker build or as valid oracle rollout evidence.
- Test package-source rewrites inside the exact pinned base root filesystem. Slim images may lack CA certificates, so switching APT to HTTPS before installing `ca-certificates` can make the first update fail; bootstrap from an immutable, repository-signature-verified HTTP snapshot or otherwise establish trust before requiring TLS.
- When the seed task and current platform review explicitly require verifier
  `no-network`, agent `allowlist`, and environment `public` modes, preserve
  those declarations. A local Docker/buildx incompatibility while building
  Harbor's sidecar is a host-tooling limitation to report and fix on a
  compatible runner, not permission to erase the task's network contract.

## Difficulty evidence and change accounting

- Set both current difficulty fields from the latest executed platform
  difficulty screen, not from the intended tier, oracle success, or a prose
  claim. After material hardening, rerun the platform screen; if a rerun is not
  available, retain the latest measured tier and state that reevaluation is
  pending rather than inventing a harder result.
- Compare the cumulative task against the seed when preparing `Files Changed`.
  If `environment/Dockerfile` changed or `environment/.dockerignore` was added
  in an earlier revision, list and explain them even when the current revision
  did not touch them. Never call cumulative environment contents unchanged
  merely because the latest edit was elsewhere.
- If the latest rollout set contains only one model family, omit the absent
  model's `pass_at_k_*` field and record the executed model's actual fraction,
  including `0/k`. Never fill an unrun model with an inferred or intended
  result.
- Reconcile every form count and claim against the final archive: fail-to-pass,
  pass-to-pass, and total required counts must match `config.json`; Files
  Changed must include every cumulatively edited artifact; and PR-expansion and
  oracle-change answers must describe additive golden-patch work truthfully.

## Archive executable-mode integrity

- Before packaging, explicitly set executable mode on every shipped entrypoint
  (`solution/solve.sh`, `tests/test.sh`, and any other invoked script). Create
  the deliverable from a terminal with `zip -rX`, excluding the archive itself.
- Inspect the completed archive with `zipinfo -l` or `unzip -Z -v` and require
  executable Unix mode bits on every invoked script. Archive extraction and
  content tests alone do not prove that execution permissions survived.

## Grading inventory

- Do not ship partial `pass_at_k` evidence with denominators below the required rollout count or inconsistent across models. Remove unsupported partial metrics instead of letting them imply a completed difficulty evaluation or fabricating missing attempts.
- Keep `grading.fail_to_pass` between 10 and 20 entries, inclusive.
- Make the declared fail-to-pass and pass-to-pass IDs match the executed tests exactly.
- Compare the union of `fail_to_pass` and `pass_to_pass` with every test that can affect reward, not only with named “required” tests. When `allow_extra_failures` is false, undeclared executed tests still gate reward and therefore make the declared graded set incomplete.
- If the 10–20 fail-to-pass limit conflicts with a larger assertion inventory, consolidate related assertions inside declared behavioral tests or intentionally run a smaller declared subset; never leave undeclared supporting tests reward-gating in the background.
- Keep regression coverage in `pass_to_pass`; do not hide failing executed tests merely by removing their IDs from configuration.
- Include genuine pre-existing repository tests in `pass_to_pass`; an injected compatibility test alone does not protect unrelated established behavior that the oracle or solver could regress.
- When selecting pre-existing tests, restore their exact bytes from the
  declared base commit after the solver-controlled phase, run every declared
  leaf, and exclude only tests whose established expectations intentionally
  change under the task. Prove the selected files pass on both base and oracle.
- Confirm every `pass_to_pass` test compiles, executes, and passes on the untouched base. When fail-to-pass coverage targets a new API, keep the injected suite base-compilable so missing API behavior fails at test execution rather than preventing all regression tests from running.
- Account for framework-generated suite/container records as well as leaf tests. If a console parser can interpret a failing `describe`/suite wrapper as an extra test, either avoid the wrapper or make the parser ignore that record; otherwise `allow_extra_failures = false` creates an undeclared reward gate.
- Measure every declared fail-to-pass test on the untouched base and move any test that already passes to `pass_to_pass`; list length alone is not evidence of 10 genuine regressions.
- Set `allow_extra_failures` to false and verify the declared test-ID union exactly matches every executed leaf test that can gate reward.
- To make executed == declared, invoke the runner with the explicit declared node IDs rather than whole test files; a file-level run drags in every sibling test and reinstates an undeclared gate. Confirm the parsed-result count in `output.json` equals the declared count on the oracle run.
- Split the invocation into one command for the fail-to-pass IDs and a separate command for the pass-to-pass IDs. Given explicit node IDs inside a module that cannot import on the untouched base, pytest exits 4 (usage error) and runs nothing at all — even with `--continue-on-collection-errors` — so a single combined command silently skips the regression tests during no-op validation. Two commands keep pass-to-pass executing and passing on the base while fail-to-pass still reports nothing.
- **When the runner emits more than one command, aggregate the worst exit status and exit with it.** A plain script returns only the last command's status, so a passing pass-to-pass command masks a failing fail-to-pass command and the no-op run reports `raw_exit_code = 0` beside `reward = 0` — exit status no longer agrees with reward, and the raw exit stops being usable as an integrity signal. Keep every command running (the regression command must still execute on an unsolved tree) but track `__rc` as the maximum and `exit "$__rc"`. Verify afterwards that the oracle reports exit 0 / reward 1 and the no-op reports non-zero exit / reward 0.
- When new fail-to-pass tests live in files that cannot import until the feature exists, pass `--continue-on-collection-errors`; without it pytest aborts the whole session on the first collection error and no pass-to-pass result is produced on the base.
- **Make the injected suite base-compilable so the no-op run reports one result per graded test.** If the new API is imported at module scope, the untouched base yields `collected 0 items / N errors` — one opaque record per *file*, no per-test signal, and a log that reads like a broken task rather than a correct no-op. Bind the not-yet-existing symbols defensively (`Name: Any = None`, real import inside `try/except ImportError`) and add an autouse fixture that calls `pytest.fail(...)` with the captured error. Every graded test then reports individually on the base and the solving agent gets a legible reason. Guard the module-level uses too: `class X(Base or object)` and `CONST = f(...) if f else <default>`.
- Determine the deferred set **programmatically** — import each module-level name against the untouched base and defer exactly the ones that are missing. Guessing misses shared types (a `SessionKey`-style TypedDict re-exported from two modules is easy to overlook) and one survivor re-breaks collection for the whole file.
- Never reach for `skipif` to achieve this: a skipped graded test is the "silent skip" auto-REMOVE pattern. `ERROR`/`FAILED` are both parsed as non-passing and are the correct outcome.

### Closing coverage gaps under the 10–20 fail-to-pass cap

- **Every named public capability needs at least one graded test.** A judge reads the instruction's capability list against `fail_to_pass` and calls a `DISCUSS`/coverage_gap the moment it can describe a plausible broken solution — stubbed helper, no-op harness, missing CLI flag — that still passes the declared set. Enumerate the capabilities the instruction promises and tick each one off against the graded IDs before packaging.
- For migration/round-trip requirements, assert each named field on the final
  re-imported object, not only on the initial legacy import. Initial parsing
  coverage does not prove that export and subsequent import preserve the field.
- **When the cap binds, consolidate per capability; never drop a capability.** Fold several narrow assertions about one capability into a single "contract" test (listing = ordering + filtering + pagination + refusal; fork = new identity + chain + slicing + title + rejection) and declare that. The narrow tests can stay in the patch as ungraded detail. Consolidating buys slots for uncovered capabilities without losing assertions.
- **A harness the agent implements and the test merely invokes is a no-op loophole.** Any published validation/conformance/self-check entry point must be graded with negative controls: run it against several deliberately broken implementations and require it to reject each. Asserting only that it accepts a correct store is satisfied by `return None`.
- **Prove the gap is closed by sabotage, not by inspection.** For each capability, stub it out in a copy of the solved tree, re-run the real verifier, and confirm reward drops to 0 *and* the intended test is the one that catches it. A sabotage that breaks a module import proves nothing — it fails everything downstream; keep the sabotage syntactically valid and semantically minimal so the attribution is meaningful.
- **Do not ship `pass_at_k_*` fields whose denominator disagrees with the field name or with the required rollout count.** A judge reads `pass_at_k_<model>` as declaring k and flags a mismatched denominator as invalid difficulty evidence, capping packaging. Remove the metric and carry the tier on a concrete `difficulty_explanation` until real rollouts exist; never invent attempts to make the fraction regular.
- **Over-strict assertions cost faithfulness points.** Where the instruction says only "must raise", do not pin the exception class or message wording — assert instead that the failure is deliberate (not `TypeError`/`AttributeError`/`NameError`/`ImportError`), which still rejects a crash while admitting any correct signalling. Likewise do not assert incidental artifacts (an extra config file copied verbatim) that the instruction never required.

### `overreach` — tests that pin how, not what

A `REMOVE`/overreach verdict means a *correct* alternative implementation would fail. Two families produce almost all of it, and both hide inside test scaffolding rather than in obvious assertions.

- **Never observe behaviour through a name the implementation chose.** Spying on `tempfile.mkdtemp` and filtering on a literal path prefix bakes in both the temp-dir helper and its naming; a correct implementation using a different prefix, or `TemporaryDirectory`, or its own scheme, fails for no stated reason. Observe through the published surface instead — here, the config directory handed to the transport — and detect leftovers by snapshotting the temp root before/after. Neither depends on a name.
- **Counting internal calls is the same mistake.** `assert len(tracked) >= 7` encodes "the implementation calls mkdtemp once per scenario". Derive the expected number from something observable (sessions actually spawned, recorded at the boundary) and assert the relationship, not a literal.
- **Distinguish your own injected errors from the implementation's.** `pytest.raises(OSError, match="spawn failed")` is fine when the test itself raised `OSError("spawn failed")` from a mock; the same construct against an error the *implementation* produces pins wording the instruction never specified. Audit `match=` sites by asking "who authored this string?".
- **Never touch the pins in pre-existing upstream test files.** Their messages are the repo's own established conventions and those tests are `pass_to_pass`; relaxing them is both out of scope and destroys regression value. Only relax pins in the tests the task injects.
- **Replace a removed message pin with a positive control, not with nothing.** `pytest.raises(Exception)` alone can be satisfied by an unrelated failure. Pair it with the same call minus the offending condition succeeding, so the rejection is attributable to the thing under test.
- **Prove it by sabotage in the overreach direction**: change the prefix / exception type / wording in the *solved* tree and require reward to stay `1`. That is the opposite of a coverage sabotage — here a passing run is the success condition. Scope the edit to the store-backed path only; rewriting a helper shared with the sync API breaks unrelated `pass_to_pass` tests and tells you nothing.

### Weak-enforcement and undocumented-artifact review findings

- **Aggregating adapter calls before asserting hides a call-shape contract.** Merging `append` calls into a per-key dict and comparing the dict accepts any number of calls that happen to deliver the right entries; when the instruction says "a single append per transcript", assert the call list itself (one call per key, entries in order). Review every test that reduces a recorded call list before asserting — the reduction usually erases exactly the property the instruction states.
- **Declared types and defaults need direct assertions, not just importability.** A published `TypedDict`/option surviving only inside the import guard is unenforced: construct each declared type with its documented fields, check identity of re-exports across modules (`types.X is X`), and pin documented default values (`Options().field == documented_default`) in a graded test.
- **A test asserting an on-disk artifact the instruction never mentions is a hidden requirement — resolve it by documenting or by removing, never by leaving both.** If the artifact is a real protocol contract (a sidecar file the CLI reads), state it in the instruction and then tighten the test to the exact documented name; if it is oracle-specific, drop the assertion for a behavior-level check. After documenting, sabotage the artifact's name in the solved tree and require reward 0 — a documented contract must gate.
- **Do not silently narrow deliberately generic instruction wording when tightening tests**; the instruction and the assertion must move together, in whichever direction is chosen.

### `coverage_gap` escalates to REMOVE — grade every imperative, not every capability

A coverage_gap verdict re-fires after each fix because the judge re-scans and quotes the *next* ungraded requirement. Capability-level coverage ("every helper has a test") is not enough: the judge enumerates individual imperative clauses in the instruction and looks for one with no graded counterpart. Two rounds of this escalate `DISCUSS` to `REMOVE`.

- **Build the matrix from imperative clauses, not capability nouns.** Split the instruction into every "must / has to / is required to" clause — thresholds and bounds, per-failure-path obligations, ordering guarantees, negative/isolation requirements, cleanup duties — and map each to a graded node ID. A single capability routinely carries five or six separately-quotable clauses; grading the capability's happy path leaves the rest citable as a gap.
- **A test that exists in `tests.patch` but is not in `fail_to_pass` earns zero credit and is actively quoted against you** ("the corresponding hidden tests exist but are not selected"). Unselected coverage reads as a deliberate omission, so either select it or fold its assertions into a selected test.
- **Under the cap, the only lever is consolidation, and each consolidated test should absorb a whole requirement cluster.** Prefer one test per cluster that walks every listed obligation in sequence — every enumerated failure path in one loop, every stated bound in one parametrised pass — over several narrow tests competing for slots. Name it `test_<cluster>_contract` so the mapping to the instruction is obvious to a reader and a judge.
- **The clusters most often left ungraded** because they look like edge cases: size/threshold-triggered behaviour, cleanup obligations on *every* abort path (spawn failure, context-manager failure, init failure, cancellation, consumer break-out), and "must not also do X" negative requirements.
- **Re-run the sabotage proof per cluster after every consolidation**, and re-check the count against the cap — folding two tests into one changes the arithmetic, and adding a cluster test can silently push `fail_to_pass` to 21.
- **Fix instruction↔test contradictions the judge finds, in the instruction.** When a test requires "return empty" and the instruction says "reject", the test is not wrong — the wording is. Restate the instruction as the observable outcome the implementation actually has to produce.
- **Avoid "copy" as a contract word.** "Must return a copy" is read by some judges as deep-copy, so a shallow copy becomes a spec violation. State what the caller may do without affecting the store (append/remove/reorder the returned list) instead.

### The terminating condition: no unselected test may assert an ungraded behavior

The judge keeps finding new gaps across rounds because it walks the *unselected* tests in `tests.patch` and reports each behavior they assert that the graded subset does not enforce. Capability coverage, then sub-clause coverage, then leftover-test coverage — each round quotes whatever remains.

- **The only stable end state:** every distinct behavior asserted anywhere in `tests.patch` is also enforced by the graded set. For each unselected test, either select it, fold its assertions into a selected contract test, or delete it. A test kept in the patch "for detail" while its behavior is ungraded is a standing citation waiting to happen.
- **Audit in that direction.** Do not only walk instruction → graded test; also walk every test in the patch → "is this behavior reachable from `fail_to_pass`?" That direction is what the judge actually runs, and it finds things the instruction-side sweep misses (concurrency bounds, timeouts on secondary calls, negative "no store configured" paths).
- **Folding is nearly free and does not consume slots.** Appending a scenario to an existing contract test closes a citation without changing the declared count. Prefer it over adding IDs whenever the behavior belongs to the same capability.
- **Keep a written test-inventory mapping and re-derive it every round.** For each test in the patch record one of: *graded directly*, *folded into `<graded id>`*, or *intentionally ungraded because <reason>*. The judge cites unselected tests by patch line range, so this mapping is what lets you show a behavior is covered even though its original test is not in the list — and it makes the next round's audit mechanical instead of a re-read.
- **Expect this to take several rounds and drive it to zero, not to "fewer".** Each pass closes the cited clauses and the next pass cites whatever is still ungraded — negative/rejection paths (unmappable input shapes, refused option combinations) and environment-precedence rules are the two families that survive longest, because they read as edge cases rather than features.
- **The terminating move is to delete the unselected tests once their assertions are folded, so `tests.patch` contains exactly the graded set.** Folding alone does not stop the citations: the judge reads the patch, sees a test outside `fail_to_pass`, and reports the behavior as ungraded regardless of whether an equivalent assertion now lives inside a contract test. Fold first, verify on the oracle, then prune. Finish by asserting programmatically that the count of test functions in the patch equals the count of declared IDs — that number reaching parity is the only reliable signal the loop is over.
- **Prune with an AST pass, and only remove classes whose name marks them as test containers.** A naive "drop classes with no test methods" rule deletes the module's fixtures, fake stores and harness classes and breaks every remaining test. Re-parse each file afterwards and re-run the suite before regenerating the patch.
- **Scope every sabotage to the exact function under test and prove it landed there.** When a sync and an async variant of a helper share the same literal, a first-occurrence `replace` silently patches the wrong one: the run still shows `reward=0`, but it was a pass-to-pass regression test that caught it, not the graded assertion you were validating — a false confirmation. Slice the source to the target function, assert the anchor is inside that slice, and print which variant changed.
- **Sabotage with semantic edits, never regex on constants.** A regex that silently fails to match produces a false "caught"/"loophole open" reading. Remove the actual guard (delete the `wait_for` wrapper, replace the call with a passthrough helper), then assert the sabotage parsed and behaves differently before trusting the result.
- **Budget wall-clock for timeout requirements.** Grading "must time out" costs the real timeout on the oracle run and the outer guard on a broken run. Keep the test's own guard well under the config `timeout_sec`, and check the total suite time still fits after adding it.
- **A graded test must fail fast, never hang.** If the behaviour under test is "the implementation bounds a blocking call", a solution that does not bound it makes the test block. The runner wraps *all* commands in one `timeout`, so one hanging test consumes the whole budget and the pass-to-pass command never runs — the reward is still 0, but the report shows every regression test missing and gives the author no diagnostic. Measure this: run the sabotage and confirm the failure is attributed to one test, not to the whole suite.
- **`asyncio.wait_for` is not a reliable escape hatch here**: it cancels the inner coroutine, and code whose drain path is written to swallow exceptions (or whose async generator close awaits the same blocked call) may not unwind. Use `done, pending = await asyncio.wait({task}, timeout=...)`, which leaves the task alone, then cancel and `pytest.fail(...)` without awaiting it. The test then returns at the bound whether or not cancellation propagates.
- Prefer asserting **elapsed time** over asserting only "it raised": wrap the call, and require both an exception and that it arrived well inside the configured budget. Otherwise an outer guard firing at 60s looks identical to the implementation honouring a 50 ms timeout.

## Verifier integrity

- Never grade pass/fail markers parsed from combined stdout or stderr. Agent-controlled builds and modules can forge those lines.
- Prefer verifier-owned structured result artifacts generated from the test framework's result objects.
- Require a successful raw test-process exit and exact equality between expected and observed test IDs.
- Fail closed on missing, malformed, duplicate, unexpected, skipped, or non-passing records.
- Delete any pre-existing structured-results artifact after the agent-controlled build and before running tests.
- Build before materializing verifier-owned tests when possible, then remove the known destination before applying `tests.patch`.
- Keep verifier harnesses, assertion shims, runners, project files, and test sources outside the solver-visible image, or overwrite them from a verifier-owned clean copy after the solver phase and before every build. Treat any solver-writable assertion implementation as a full-reward bypass.
- Do not expose a collision-prone graded test destination in a solver-visible project file. If the destination must be named, remove any solver-created file before applying the verifier patch and build only from verifier-owned copies.
- Require the outer verifier timeout to be at least as long as the test command's inner timeout so the inner guard can report a test failure instead of being preempted as infrastructure failure.
- For pytest, run a verifier-owned copy from a freshly recreated directory outside the solver-controlled `conftest.py`/configuration tree, disable third-party plugin autoload, and use isolated Python startup. Grade a verifier-owned JUnit/XML artifact rather than console markers.

## Scripts and repository hygiene

- Run `git fsck --full` without `--no-dangling` and require completely empty output. A clean status, pruned refs, absent reflogs, and `git fsck --no-dangling` do not detect loose answer/test blobs.
- Treat blob IDs printed on `index 0000000..<sha>` lines in verifier or oracle patches as leakage probes: none may resolve through `git cat-file -e <sha>` in the packaged checkout unless the blob is legitimately reachable from the base history.
- Never stage oracle or hidden-test material in a worktree that shares the packaged repository's object database. Generate patches in a disposable `git clone --no-local`, then rebuild or freshly clone the shipped checkout from reachable base objects and repeat silent `git fsck --full` before packaging.
- After any patch-generation, solve, or three-way-apply validation, expire reflogs, prune unreachable objects, and remove transient `ORIG_HEAD`/`AUTO_MERGE` state before packaging. Then extract the final ZIP and require plain `git fsck --full` to produce no output there; checking only the source checkout or using `--no-dangling` is insufficient.
- Treat the `.git/logs` path itself as a packaging failure, even if all reflog files appear empty. Ref-deletion commands can leave nested logs such as `.git/logs/refs/remotes/origin/HEAD`; after the last ref-mutating command, delete the entire `.git/logs` tree and require both `test ! -e environment/repo/.git/logs` and no `environment/repo/.git/logs` prefix in `unzip -Z1` output.
- A verifier that reads the packaged base commit must account for container ownership changes. Invoke repository-local Git operations with a command-scoped `safe.directory=<workspace>` setting; otherwise `git apply` may silently fall through to `patch` while the later `git show <base>:<path>` restoration fails as a dubious-ownership error. Exercise the verifier under the container's actual user/ownership boundary when available.
- Do not make pass-to-pass restoration depend exclusively on runtime Git history. If the platform can omit, relocate, restrict, or partially expose `.git`, carry verifier-owned byte snapshots derived from the declared base commit inside an allowed verifier artifact, validate their fixed digests, and atomically overwrite the selected regression files after the solver-controlled build. Prove the path by corrupting every selected file, making `.git` unavailable, and requiring the full oracle inventory to pass.
- `solve.sh` must not apply `golden.patch` in reverse as a fallback. A second solve must not duplicate the fix or silently mutate a solved tree.
- Remove a verifier-owned new-file test path before applying `tests.patch` so agent-created collisions cannot produce three-way conflict markers.
- Enumerate every `new file mode` path in `tests.patch`, delete those exact verifier-owned destinations before patch application, and execute a collision simulation in which all destinations pre-exist before the verifier runs.
- Do not trust `patch --reverse --dry-run --batch` alone for retry detection: GNU patch can ignore `-R`, validate the forward direction, and return success while the test is still absent. Pair explicit reverse mode with `--forward`, or use an exact `git apply --reverse --check`, before treating a verifier patch as already applied.
- **`ls -l` is worthless for executable bits on a WSL/drvfs (`/mnt/<drive>`) checkout — every file reports `777`.** Read the recorded mode instead: `git ls-files -s` for tracked files, and the ZIP's own `external_attr >> 16` for packaged ones. A task can look perfectly executable in the working tree and ship `solve.sh` at `100644`, or at mode `0o0` in the archive.
- **Verify the archive's stored modes explicitly before delivery**, not just its contents: `(info.external_attr >> 16) & 0o777` must be non-zero for every entry, `0o755` for `solve.sh`/`test.sh`, and must match `git ls-files -s` for everything inside the embedded checkout. A zip written without setting `external_attr` stores mode `0`, so extraction yields non-executable scripts and the harness's solve step silently does nothing.
- **A silently-skipped solve step is indistinguishable from an unsolved run**: the oracle reports every fail-to-pass test failing to import, which reads like a broken task rather than a packaging fault. Give `solve.sh` a self-verification tail that fails loudly when the patch did not take effect. Verify by **inspecting the source tree** (expected files exist, expected names appear in `__all__` via `ast`), never by importing the package — importing drags in third-party dependencies, so an unrelated dependency problem gets misreported as "the patch did not apply".
- After rebuilding an archive, extract it to a native filesystem and run the whole oracle **from the extracted copy**, invoking `solve.sh` as an executable rather than via `bash solve.sh`. That is the only path that exercises the mode bits the harness depends on.
- Confirm the embedded repository is clean, at the declared base commit, and has no temporary worktrees, remotes, reflogs, or unrelated artifacts.
- Verify both patches apply to a clean base and keep `instruction.md` byte-identical to `environment/problem_statement.md`.
- Preserve required tracked upstream files, including tracked editor configuration.
- During archive validation, compare every extracted tracked file mode against `git ls-files -s` with `core.filemode=true`. A clean `git status` is insufficient when the shipped Git config disables file-mode tracking.
- Run `git fsck --full --no-dangling` and inspect every ref path directly; remove broken or all-zero remote-tracking refs even when `git remote` and `git rev-list --all --not HEAD` appear clean.

## Task quality and packaging

- Treat `tests/` as a schema whitelist, not a general verifier-assets directory: before packaging, assert that it contains only the platform-allowed entries (currently `config.json`, `grade.py`, `test.sh`, and `tests.patch`). Materialize any harness/support files from an allowed verifier-owned artifact instead of shipping extra subdirectories.
- State observable requirements—the WHAT—without prescribing libraries, implementation methods, internal sentinels, or literal legacy details the agent should discover.
- Compare instruction and test scope against the complete source PR diff, including UI wiring, state, localization, and secondary feature paths. A well-tested subsystem is still a scope reduction when the source PR delivers a broader integrated feature.
- Do not mark a task unfixable merely because it covers only part of a broader source PR. If validity can be restored by a natural additive expansion using material already present in the PR, classify it as Fixable; reserve Not Fixable for cases whose only remedy is reducing, replacing, or leaving the anchored scope.
- Pin every Docker `FROM` image by immutable digest in addition to a readable tag; a mutable major-version tag such as `node:22-slim` is not reproducible pinning.
- Avoid exhaustive public symbol inventories and verbatim type definitions unless each name and shape is an established compatibility contract. Prefer capability-level acceptance criteria and test through the package or product boundary.
- Describe recoverable versus unrecoverable edge cases behaviorally. Do not reveal the exact internal exception type, status code, sentinel, branch, or root-cause signal when a competent agent can discover it from repository and dependency behavior.
- Avoid prescribing per-iteration control flow or enumerating an oracle-specific diagnostic layout. State observable gating and diagnostic goals, then ensure tests accept any implementation that provides equivalent useful context rather than matching the golden patch's exact phrases or fields.
- Phrase polling gates as avoided observable waste (for example, no unnecessary reads while data is absent), not as a mandated check order or internal sequencing rule.
- Describe resilience as tolerating temporary unavailability without masking genuine errors; do not pre-classify the exact transient and fatal signals the implementation should discover.
- Do not pin a conventional delegate type or exact validation-exception class unless it is an established public compatibility contract. Describe the callable semantics and null-validation requirement, and make tests accept compatible delegate shapes and an appropriate exception family.
- Prefer stating a caller capability over dictating an API construction pattern. Do not require an overload, optional parameter, builder, or other shape unless that shape is itself a public compatibility contract; make tests discover compatible callable forms.
- When correct and efficient polling already follows from the task's outcome, omit existence/download gating entirely. Even “avoid unnecessary reads” can reveal the check ordering the agent should discover.
- Express rejection behavior as the positive return invariant: return only content that meets the caller's condition. Do not spell out the branch taken when the condition is false.
- Prefer “handle transient failures gracefully” over contrasting temporary and genuine errors unless propagation behavior is an externally documented contract.
- State only that useful diagnostics must be preserved unless particular fields or caller-message composition are a public contract; tests should not require an oracle-specific diagnostic layout.
- Do not spell out internal tensor layouts, scoring formulas, dimension-comparison pitfalls, or other format-disambiguation logic when compatibility with a standard model/export format states the observable contract sufficiently.
- Describe normalization and reliability in terms of suitable outputs and graceful behavior; avoid pre-answering pathological numeric guards, cleanup/session strategies, or repeated-run failure mechanisms.
- Require a particular runtime/dependency name or version constant only when it is an established public compatibility contract. Otherwise state the deployment behavior and let the implementation choose the runtime and loading design.
- Do not let hidden tests force an oracle-specific internal API that the instructions intentionally omit. Prefer command/public-boundary tests over compiling against newly introduced result structs, interface signatures, internal fields, namespaces, or helper overloads.
- If a test must pin an exact name, confirm that it is a genuine user-facing compatibility contract and state that contract in the instructions; otherwise test only observable behavior.
- Exercise every promised mode through the same behavioral scenario. In particular, an EOF-only test does not cover a temporary-lull requirement, and one input mode cannot stand in for another.
- Never modify pre-existing regression test files in `tests.patch`; add verifier-owned files instead. If the oracle breaks existing tests unless imports or helpers are changed, preserve the original source API in the oracle.
- Keep difficulty evidence consistent with `model_difficulty`; record actual rollout evidence rather than unsupported estimates.
- Keep legacy and current difficulty aliases identical. Remove malformed or non-standard rollout fractions rather than fabricating attempts, and support the tier with a concrete `difficulty_explanation`.
- A pass-to-pass list made only of tests injected by `tests.patch` is not a base regression guard. Include genuine tests present at the declared base, run their exact IDs on both NOP and oracle states, and ensure only the explicitly declared union executes.
- Preserve network metadata when the current platform contract explicitly requires verifier `no-network`, agent `allowlist` plus its required model host, and environment `public`; validate all three blocks together after any metadata rewrite.
- Reconcile form prose against the final cumulative artifacts: describe instruction rewrites as rewrites, not unchanged text, and derive every quoted F2P/P2P/required count directly from the packaged `config.json`.
- Re-run Oracle and no-op validation after verifier changes, including an explicit forged-output attack test.
- Treat framework reports written below the agent workspace (for example Surefire or JUnit XML under a build directory) as untrusted grading input. Production code can forge a later report even when the original tests and build manifest are hash-protected.
- For report-forgery-resistant grading, invoke each declared test selection through the real runner, capture that invocation's exit status in verifier-owned control flow, and synthesize the structured result from the exit status rather than rediscovering test outcomes by scanning workspace reports. Preserve every invocation's status so a later parser command cannot mask an earlier failure.
- Ensure the final ZIP excludes any nested source ZIP, preserves executable bits on `solve.sh` and `test.sh`, parses all JSON/TOML, and passes archive integrity checks.
- Ensure the final ZIP includes the embedded checkout's clean `.git` directory; excluding Git metadata breaks the expected agent and patch workflow. Re-audit refs, remotes, reflogs, filters, unreachable objects, and HEAD/base alignment inside the packaged copy.

## Agentic-judge coverage and faithfulness

- For ordered categories with different comparison rules, state rule precedence and scope explicitly (for example, cross-category ordering versus within-category tie-breaking). Do not let a graded edge case depend on two plausible readings of overlapping rules.
- Build an instruction-to-test matrix before packaging. Exercise every promised runtime mode independently, including negative isolation requirements such as one startup path not activating another path's process-wide behavior.
- Build a test-to-contract matrix as well: every exact export/type name, state key, menu or command ID, localization key, interpolation token, module path, component filename, and URL pattern asserted by a test must either be stated as an established public compatibility contract or be replaced with an outcome-based assertion.
- Perform a correct-alternative freedom audit before packaging: a solution that preserves the specified public behavior but renames internal helpers, reorganizes modules/components, chooses different internal state or i18n keys, or uses another genuinely immutable hosting format must not fail unless that exact choice is explicitly part of the contract.
- Do not use a component's expected source filename as the browser-build entry point unless the filename itself is a required public artifact. Prefer building the established application/package entry point and exercising the feature through public menu, command, state, or rendered UI behavior.
- Treat token presence in generated bundles as supporting evidence only. Menu, command, lazy-panel, progress, cancellation, and map-update requirements need behavioral or public-registry assertions that distinguish working integration from dead strings or unused imports.
- Match localization coverage to the wording of the instruction. A promise covering descriptions, inputs, progress, results, and errors needs representative checks for every group; otherwise narrow the promise. Do not require a particular translation-object layout or placeholder spelling unless it is explicitly public.
- Test URL immutability by the stated guarantee or enumerate accepted immutable schemes. Do not equate “immutable HTTPS location” with one provider-specific 40-character commit-path regex unless that exact format is required.
- A positive reference to a legacy initializer does not prove that the same mode avoids a new initializer. Test both sides of mode ownership through observable execution, linkage boundaries, or a complete call/dependency path.
- Do not use source-token or symbol-vocabulary allowlists as the sole proof of concurrency, interrupt safety, locking semantics, or performance characteristics. Prefer behavioral stress/interleaving tests or platform-facing semantic checks that admit any correct primitive.
- Do not require an unstated internal source location, initializer name, parameter shape, or callable signature. Discover implementation relationships where necessary, or test through established public and ABI boundaries.
- Do not require a compatibility symbol to disappear when the actual contract is that it no longer imposes a fixed capacity ceiling. Test that the limit is behaviorally inactive and that full supplied capacity remains usable.
- Clarify observable meanings of capacity, startup readiness, shutdown, and locking requirements enough to make tests unambiguous, while leaving implementation mechanism and code location for the solving agent to discover.
- Treat a single judge score of 3 or below on coverage or faithfulness as a required revision even when another judge scores the same suite highly; resolve the cited counterexample rather than averaging it away.
- A cleanup test must prove the complete production lifecycle path reaches the cleanup behavior. Testing a finalizer in isolation, or merely finding any reference between its source component and a lifecycle component, does not prove normal shutdown invokes it.
- Do not require a new component to occupy a dedicated directory or require a startup hook to call exactly one helper per concern. Verify that the behavior is present in the built artifact and works through the established public lifecycle boundary, allowing direct, combined, or indirect implementations.
- Negative startup-isolation checks must cover transitive call paths through shared initializers; checking only direct symbol references can miss an indirectly activated forbidden behavior.
- Do not forbid a harmless legacy cleanup call when the requirement only assigns initialization ownership. Keep negative assertions scoped to the lifecycle phase and observable interference named by the instruction.

## Prescriptiveness judge — recurring flagged patterns

The in-app prescriptiveness judge scores `instruction.md` on a 0–1 scale and cites Rule 3 (prescribes the approach) and Rule 5 (pre-answers what the agent should discover). It is advisory and does not block submission, but resolve every finding before review. These six patterns are the ones it actually flags; check each one before packaging.

- **Do not enumerate the failure cases of a mapping/parsing function.** Listing every shape that must return `None`/error — part counts, missing suffixes, "exactly three segments" — hands over the whole classification. State the positive shapes the function accepts, then one sentence: anything that does not unambiguously match returns `None` instead of a guessed result. Add "and no input may make it raise" when total-ness is the real contract.
- **Do not name the stdlib call or exception type behind an edge case.** "`os.path.relpath` signals this with `ValueError` — catch it" tells the agent the implementation. Describe the situation behaviorally ("a path that cannot be relativized against the root is simply unmappable"). Corollary: a test that monkeypatches a specific stdlib function to force that branch is itself over-binding — prefer a test that feeds a genuinely unmappable input, and never leave such a test in `fail_to_pass`.
- **Do not enumerate attack strings for a security guard.** `""`, `/etc/passwd`, `../escape`, `a/../b` is the threat model, and producing it is part of the work. State the invariant and where the input comes from: these values are untrusted, nothing may be written outside the sandbox directory, and a bad value is rejected rather than sanitized into something writable.
- **Do not specify a component's internal design when only its observable contract is graded.** Buffer-then-flush splits, "fire-and-forget" background work, "await any in-flight flush", explicit queue/lock structure — all are HOW. Keep the public method names the tests call plus any constant whose exact value is asserted, and re-express the rest as end-state guarantees: what has provably reached the adapter by the time a call returns, ordering, exactly-once delivery under any interleaving, no phantom call for an empty batch, and the backlog bound that forces early delivery.
- **Do not name the specific field to redact in a credential/secret path.** Naming the key to strip and the key to keep removes the security reasoning. State the outcome: the copied credential must still authenticate while long-lived renewal secrets stay out of the destination.
- **Do not spell out a selection algorithm** (sort key, filter, tie-break) when the outcome is observable. "Most recently active real conversation, deterministic for a given set" replaces "highest mtime, skip sidechains, break ties deterministically". Keep the word *deterministic* — it is an observable property — but drop how the order is computed.
- **Do not pre-answer Unicode/encoding normalization.** "Composed versus decomposed spellings must match" names the corner case; "any two spellings that name the same directory must collapse to a single key" states the contract and leaves the discovery.
- **Counter-rule — never trade prescriptiveness for hidden requirements.** Keep every module path, public/dunder-private symbol, CLI flag, env var name, and numeric constant that a shipped test imports, monkeypatches, or asserts. Removing those to score better converts an advisory Minor into a Major (unsatisfiable task). If the judge flags such a name, the correct fix is to rewrite the *test* toward a public boundary, not to delete the name from the instruction. Before each edit, grep the test suite for the token you are about to remove.
- After any de-prescriptiveness edit: re-copy `instruction.md` to `environment/problem_statement.md` byte-identically (verify with `cmp`/`md5sum`), grep the instruction for the removed tokens to confirm none survive, and re-run oracle + NOP + grader so the reward pair is still 1.0/0.0.

### The judge escalates — expect a second round that targets names, not prose

Once the procedural prose is gone, the judge re-scores and flags the identifiers themselves: internal module paths, the implementation class and its constructor/method names, underscore-prefixed helpers, and module-level constants. Do not reflexively delete these. Classify every finding first.

- **The hard boundary is a test file's module-level import block.** Any symbol imported at module scope is required by *every* test in that file, so deleting it from the instruction fails the import and takes all of that file's `fail_to_pass` tests with it. A symbol only referenced inside one undeclared test body is far weaker and can usually be generalized away.
- **Run this classification mechanically, do not eyeball it.** AST-parse each verifier test file, collect top-level `ImportFrom` names for the SDK package, subtract the symbols that already exist on the untouched base (verify by actually importing them against the NOP tree, not by memory), and assert every remaining name appears verbatim in `instruction.md`. Any gap is a hidden requirement.
- This check finds pre-existing defects, not just self-inflicted ones: it caught a dataclass returned by a new public-ish entry point that the *original* instruction had never mentioned, whose absence would have failed a whole test file's imports. Run it on every task, including before the first edit.
- **Structural mitigation that is safe:** keep the body purely behavioral and collect every fixed identifier into one labelled appendix that states *why* each is fixed — external CLI/protocol contract, the parity target being mirrored, or the layout the repository already uses. This removes the Rule 3/5 procedural density (step sequences, "where" localization, algorithm spelling) even where the name itself must survive, and it reads as an integration contract rather than dictated file layout.
- **Accept the floor and say so.** When every remaining finding is a bound name, the score cannot reach zero findings without rewriting the test suite toward public boundaries. Report which findings were fixed, which are load-bearing and why, and offer the test rewrite as an explicit scoped decision — never silently delete a bound name to improve an advisory score.
- Findings that are almost always genuinely fixable even in the second round, because their tests are undeclared or assert only outcomes: retry/errno strategies, title-derivation fallback cascades, uuid-remapping mechanics, on-disk path templates the repo already reveals elsewhere, and "where in the pipeline" localization such as naming the receive loop.

### Rewriting a white-box suite onto the public boundary

When the decision is to remove the bound names rather than keep them, do not rewrite the tests from scratch — the assertions are the valuable part and re-deriving them loses coverage.

- **Use a test-local adapter.** Replace the internal entry point with a small class/function in the test file that drives the real public entry point and exposes the same attributes the old tests asserted against. A `materialize_x()` call that returned an object with `config_dir`/`cleanup` becomes a `_stage()` helper that connects through the public client with the subprocess stubbed, reads the same values off the options handed to the transport, and cleans up via `disconnect()`. Every existing assertion then survives a one-line call-site substitution, and the test is genuinely stronger because it now exercises the wiring too.
- **Detect "did nothing happen" by comparing before/after, not by a sentinel.** The adapter cannot return `None` just because a field is absent — the caller may legitimately have set it. Compare the value that reached the boundary against the value the caller supplied.
- **Test helpers that poke store/adapter internals are hidden requirements too.** Seeding order via a private `_mtimes` dict is no better than importing a private function. Subclass and override the *protocol* method instead — an adapter deciding what it reports is ordinary published behaviour.
- **Delete, do not weaken, a test that can only exist white-box.** A test that monkeypatches a private helper to force a platform branch (keychain, registry, syscall) is unsatisfiable by any alternative implementation. Remove it and say so, rather than leaving a test no correct agent can pass.
- **Removing a constant from the tests can create a hidden requirement in the other direction.** Once the suite stops importing a threshold constant but still depends on its magnitude behaviourally (small batch buffered, large batch delivered eagerly), the instruction must state the threshold. Thresholds are explicitly on the keep-list — state the *value* as a contract, not the constant's *name*.
- **Verify the hidden-requirement sweep in a clean interpreter.** Probing "does this symbol pre-exist on the base?" from a process that already imported the solved tree gives false positives; run it as a fresh subprocess with only the base `src` on the path.
- Re-derive the declared test IDs after the rewrite — class and method names move — and re-run the executed-equals-declared check plus the oracle/no-op reward pair before believing any of it.

## Production-code / verifier-patch separation

- Compare the complete source-PR diff with the union of `solution/golden.patch` and `tests/tests.patch`. If the verifier patch supplies production implementation that the instruction asks the solver to create, the task is unsolvable as packaged even when the two patches reconstruct the PR together: a correct solver can collide with verifier-created files, while the oracle is not self-contained. Move the complete production change into `golden.patch` and keep `tests.patch` limited to independent verifier-owned tests.
- Re-test `tests.patch` on both the untouched base and the fully solved oracle tree. A new-file verifier patch that applies only to the base but collides with the required solution is not patch-safe.
- When a cross-platform build-system contract cannot execute non-native binaries, validate the public configuration/build surface by configuring with the repository's toolchain modes and asserting the generated target inventory. This is stronger and more implementation-neutral than source-token scans; keep native runtime coverage for the host architecture as well.
- Audit `.git/modules/**` independently of the main checkout. Removing an untracked submodule worktree or its stanza from the parent `.git/config` does not remove the nested repository, which can still ship unrelated objects, refs, and remotes. The final archive listing must contain no orphaned nested Git module.

## Reproducible build environments

- Pin downloaded toolchains to an exact version and immutable artifact URL, and verify the artifact against its publisher-provided checksum. Mutable selectors such as `latest` or an SDK `--channel` do not define a reproducible environment.
- When an environment build fails before trials begin, replay the Dockerfile from its exact digest-pinned base and isolate the first failing layer. Prefer copying a versioned toolchain from a digest-pinned image stage over an ad-hoc `RUN curl`/`RUN wget` download; build sandboxes may permit base-image pulls while blocking arbitrary download hosts.
- Point OS package-manager sources at an immutable repository snapshot before resolving packages; a digest-pinned base image does not freeze subsequent installs from a rolling mirror.
- Do not run a package-manager install during image construction when the bundled manifest has no dependencies. Unnecessary registry resolution adds mutable network state without adding anything to the runtime.

## Prescriptiveness feedback must update the verifier too

- When an automated prescriptiveness review flags an algorithm, private API, source-file layout, internal naming prefix, or failure signal, grep the verifier before editing the ticket. Remove or replace any white-box test that binds the same detail; deleting only the prose creates a hidden requirement.
- Preserve the underlying acceptance claim through public executables, registered build targets, output contracts, dependency behavior, and end-to-end error handling. Re-derive the declared test inventory, then repeat clean-base NOP, oracle, exact-inventory, and archive validation after the rewrite.
- If a later judge flags even the storage model, encoded width, or the fact that two build modes yield different reference data, remove verifier assertions for those representation choices as well. Grade the public validation target and failure outcome without forcing repository files, digest widths, or cross-mode data relationships.
- A successful validation target is not evidence that it detects drift: a no-op executable can satisfy build, registration, repeatability, and dependency checks. Add a representation-neutral negative control that alters results at a public linkage boundary and require the real registered test to fail. Exercise unsupported-instruction behavior only through a genuine platform-availability boundary. Cover every shipped architecture mode, including scalar-only configurations, and verify newly promised ABI counterparts from generated/public artifacts rather than source tokens.
- Apply a family-wide invariant to every declared variant, not only a representative scalar path; otherwise functional scalar code plus stub FMA/vector targets can still earn full reward. Do not simulate unavailable hardware by injecting an arbitrary illegal instruction into an otherwise portable function call: that over-binds the implementation. Either exercise a genuine platform-availability boundary or omit/narrow that contract. When cross compilers are absent, promise and grade cross-configuration target exposure rather than claiming the verifier proves those targets compile.
- Dead imports are not execution coverage. If an interposer records no calls, accept that only after proving the host lacks the target's documented CPU features; a supported target with imports that are never reached must fail. This closes the no-op-plus-dead-symbol bypass while retaining clean behavior for genuinely unavailable ISA variants.
- One shared “any function called” marker does not prove every promised function and precision participates in validation. Perturb each operation/precision independently, require each perturbation to fail the registered test, and record more than one input spanning both signs. This rejects dummy imports and one-input validation while remaining independent of the reference-data representation.
- Treat an explicit “do not regress” list as a coverage list, not boilerplate. Every named legacy tester or tool family needs a selected pass-to-pass record that at least builds and executes a representative established flow; unrelated compatibility targets do not stand in for it.
- Compare automated-review citations with the exact artifact being packaged before revising. A delayed report may describe an older verifier; retain and demonstrate an already-landed stronger fix, then address only counterexamples that still apply to the current patch.
- When a legacy pass-to-pass tool no longer compiles against a newer system dependency, a verifier-owned compatibility include/compiler wrapper may restore the historical build semantics without modifying the shipped base. Keep the shim outside production, run the real legacy executable, and validate both untouched base and oracle under the same wrapper.
- A difficulty expansion must add implementation work, not merely grade behavior the oracle already provides. Probe candidate requirements against the current oracle first; prefer cohesive, observable dimensions such as edge-value coverage, optional dependency fallback, and shared/static linkage, then update the oracle, instruction, tests, and metadata together.
- Before calling a deterministic-snapshot relationship part of the contract, generate snapshots from every runnable target. Equal FMA/no-FMA labels do not guarantee byte-identical results across scalar and vector algorithms or accuracy tiers. Unless cross-target equivalence is an established public guarantee, require repeated per-target stability, read-only self-validation, offline expectations for each distinct result family, and fail-closed parsing rather than imposing a false shared snapshot.
- When difficulty is raised by extending an operation family to another accuracy tier, grade every operation/precision/tier combination independently at the public linkage boundary. Prove the increase with two minimal solved-tree mutations: omit the new tier and weaken one lifecycle rejection, then require the real verifier to assign reward zero with attributable failures.
- An optional-backend requirement needs two isolated configurations: prove the available backend is actually used in the enabled build, and explicitly disable discovery to prove the self-contained fallback still builds and accepts the same behavior. Merely running once on a host where the dependency happens to be installed does not exercise both paths.
- Broad domain sampling does not prove exact boundary coverage. When signed zero and closed-domain endpoints are promised, observe their exact public-ABI bit patterns independently for every promised precision; generic positive/negative counters can miss `-0`, `+0`, or an excluded upper endpoint.
- When a provider named in the instruction is not itself a public compatibility contract, remove both the provider mandate and any verifier assertion that requires its use. Grade the configuration, dependency, and behavioral outcomes instead so another valid backend can pass.
- Ask for thorough domain coverage without enumerating the boundary cases an implementer should discover. A representation-neutral verifier can require dense sampling across the domain and independent operation/precision checks; reserve exact magic inputs for an explicitly stated public contract.
- Describe a dependency-unavailable build by its observable constraints and successful outcome. Do not mandate a “fallback,” “self-contained” path, or other internal strategy; after generalizing the prose, rename verifier records and diagnostics that still encode that strategy and repeat the oracle/NOP inventory check.
- A full-domain promise is family-wide when the instruction names scalar, FMA, and vector variants. Apply the same density/distribution assertion independently to every runnable native variant and every promised operation/precision; a strong scalar observer plus a two-point vector check leaves a stub-vector loophole.
- Proving that optional numerical dependencies are absent at runtime does not prove the advertised configuration builds without their development headers or link libraries. Configure with discovery/cache inputs disabled and compile in an isolated or guarded include/link environment, then run the resulting targets and inspect their runtime dependencies.
- Keep dependency-unavailable compiler guards semantic: block the actual headers and linker inputs, not broad substrings in source paths, defines, or filenames. A correct self-contained implementation may legitimately use compatibility-oriented names without depending on the external package.
- When a native test can cleanly succeed because the host lacks its ISA, scope saved-result, drift, and domain-coverage promises to host-executable extensions. State the unsupported-host success/no-crash contract explicitly, and ensure every CPU-feature gate uses the same feature map.
- Qualitative wording such as “enough coverage to catch localized drift” does not justify exact sample-count, region, or bin cutoffs. Either publish those measurable acceptance thresholds in the instruction or replace the verifier with a genuinely threshold-free behavioral check.
- A drift-rejection test does not prove that expected values are fixed independently of the current invocation: a tester can compare library output with a host math function computed at runtime and still reject an interposed library result. When invocation-independent offline expectations are promised, perturb the ambient reference provider while leaving the product library unchanged and require supported validation targets to keep passing; also retain the opposite control that perturbs the product library and requires failure.
- A new fail-to-pass control can vacuously pass on the untouched base when its subject artifact is absent and the underlying runner treats an empty selection as success. Make the control first prove that the required artifact/public entry point exists, then execute the behavioral scenario; re-run the full no-op inventory and require every declared fail-to-pass ID—not merely reward overall—to be non-passing.
- Do not describe a new counterpart as joining an undefined “deterministic API.” Identify the existing family through a discoverable public boundary and state the counterpart relationship in ABI terms (operation, precision, width, accuracy, extension, and calling convention) without prescribing internal symbol prefixes or source locations.

## Session snapshots and atomic filesystem transitions

- A stable per-session view is not proved by retaining a host pathname. After creating the view, modify and remove the host file and require earlier sessions to keep the captured bytes and metadata while a later session sees the new snapshot. Pair this with a large shared input and a traced-memory bound so an implementation that copies the same immutable bytes into every session cannot pass.
- Treat replacement overlays as a three-way reconciliation, not a reset. Grade session-owned replacements, tombstones, moves, and metadata changes against a later conflicting overlay; also prove untouched operator-only paths retire, untouched bundled paths restore, and concurrent views remain unchanged.
- “Rename replaces the destination” is incomplete without type and topology safety. Cover non-directory-to-directory, directory-to-non-directory, non-empty directory replacement, empty-directory replacement, and a directory moved below itself; every rejected transition must leave both subtrees unchanged through each promised public adapter.
- For console-forgery validation, make the sabotage emit an exact fake pass marker during the failing call so the marker is demonstrably present in captured logs. Require verifier-owned structured results to retain the real failed status, nonzero exit, and zero reward despite that marker.

## Verifier-owned completion and transactional-builder hardening

- A per-test process exit code is not sufficient by itself when production initialization can terminate successfully before the selected test runs. Wrap each declared test from verifier-owned source and require both exit zero and a random verifier-owned completion token written only after the target returns; missing or incorrect completion must fail closed. Confirm with a forged-output/early-success attack.
- When restoring genuine pass-to-pass tests from the base commit, remove solver-controlled test files first, restore each selected upstream file byte-for-byte with command-scoped `safe.directory`, and invoke only the declared leaf through a verifier-owned wrapper. Re-run on base and oracle and require the exact declared ID inventory.
- For builders that publish multi-stage mutable output, hardening should test failure atomicity at early, middle, and late validation stages: no panic, no partial publication, no mutation/replacement of a prior successful snapshot, and successful reuse after correcting the rejected input. Pair this with bidirectional ownership tests for mutable extension/plugin inputs.

## Git-metadata-independent oracle and verifier execution

- Do not assume Harbor preserves or exposes `.git` at `/app`, `/testbed`, or `/workspace`. A `.git` directory existence check is not proof of a usable repository: validate `git rev-parse HEAD` when metadata is available, but provide a fail-closed working-tree identity fallback for runtime execution.
- When an image provides a baked compatibility workspace such as an `/app` symlink, do not let it outrank real platform mounts such as `/testbed` or `/workspace`. Validate oracle behavior with both a pristine baked tree and a separately mounted solved tree present; otherwise the verifier can report a clean NOP-style reward of zero after successful patch application.
- Any verifier that restores upstream pass-to-pass tests must carry integrity-checked verifier-owned byte snapshots (or an equivalent immutable source) rather than requiring the runtime Git object database. Continue to audit the packaged repository HEAD and Git hygiene separately before packaging.
- Apply oracle and verifier patches through a Git-independent unified-diff path when the environment includes `patch`; test both forward and reverse dry-runs so missing Git metadata does not discard otherwise valid oracle trials.
- For legacy GOPATH projects, stage the selected agent working tree into a verifier-owned canonical import path before running tests. This preserves agent changes, isolates verifier-owned tests, and avoids platform mount layouts silently resolving internal imports from a stale image copy.
- Enforce the task-schema allowlist before packaging: when `tests/` permits only `config.json`, `grade.py`, `test.sh`, and `tests.patch`, do not add snapshot directories or helper files there. Embed small integrity-checked snapshots in an allowed verifier entrypoint, or use another schema-approved representation, and inspect the archive's immediate `tests/` entries explicitly.
- A promise to preserve an existing security mount profile requires option-level coverage for every named or profile-defining mount, not merely destination presence plus one representative read-only flag. Check type, source, and the complete security-option set where those values are compatibility behavior.
- Verify source metadata by opening the actual upstream PR page; do not infer the repository owner from language import paths. Organization moves and import-path compatibility often make those names differ legitimately.
- Scan the whole task directory (repo, vendor, test fixtures) for private-key material before packaging: `grep -rlE 'BEGIN (RSA |EC |DSA |OPENSSH |ENCRYPTED )?PRIVATE KEY'`. The agentic judge hard-caps packaging at 1/5 for any private key anywhere in the task directory, even upstream self-signed test CAs. Decision (2026-08-17, bcef664e): delete every private-key file from the working tree, keep public certs, and confirm nothing on the graded build/test path loads the deleted file. Never commit the deletion — HEAD must stay at the declared base commit for the verifier identity check; a working-tree-only deletion is the accepted state. Note the resulting dirty `git status` in the review answer rather than hiding it.
- Do not use `//go:linkname` to mutate unexported dependency state in graded tests; linker enforcement varies by Go release and can make a correct oracle fail only on the target runner. Prefer an integrity-checked verifier-owned dependency-boundary probe in the disposable staged tree, and prove both that the untouched base triggers it and that the oracle avoids it.

## Go verifier isolation and constrained-host validation

- When the source change intentionally updates existing upstream tests, do not ship those edits in `tests.patch`. Put fail-to-pass coverage in new verifier-owned files, exclude only the obsolete expectations, and restore unaffected base tests from integrity-checked snapshots as genuine pass-to-pass guards.
- New Go APIs must not make the untouched base fail at package compilation before individual graded tests run. Resolve the named public method dynamically inside each verifier test when necessary, then fail that test explicitly if the API is absent; verify that the NOP report contains one non-passing record per declared fail-to-pass ID and passing records for every regression ID.
- For `go test -json`, accept only terminal `pass`/`fail`/`skip` events with exact package-and-test identities, require a successful raw process status, and reject missing, duplicate, skipped, or unexpected records. Prove console-forgery resistance by printing an exact fake JSON pass object from production initialization and confirming Go wraps it as an `output` event while reward remains zero.
- Do not assume `/tmp` has usable capacity on shared runners. Place verifier staging, `TMPDIR`, and `GOTMPDIR` under the verifier artifact volume, bound each package command, and re-run NOP/oracle after changing temporary-storage paths.
- On WSL/drvfs, first prove an all-dirty checkout is mode-only before setting repository-local `core.filemode=false`; then re-run `status`, inspect every ref file, and run plain `git fsck --full`. A dangling symbolic remote HEAD can survive after remotes are removed and must be deleted before packaging.

## Node verifier and vendored-runtime lessons

- A `node:test` module that constructs its harness at top level can collapse the untouched-base run into one collection failure instead of one result per declared contract. Defer missing-symbol extraction and harness construction into each selected test callback, invoke every declared case separately, and require every fail-to-pass ID to produce its own non-passing NOP record while genuine upstream regressions still execute.
- Do not grade TAP text from stdout, even when the regular expression is exact. Run each declared Node contract under verifier-owned control, require a non-forgeable random completion token written only after its callback returns, combine that with the raw process exit, and build `output.json` directly from those statuses. Prove the guard by emitting an exact fake `ok` marker from a failing production path and requiring reward zero.
- When the source scope includes regenerated vendored browser runtimes, an air-gapped agent must receive the lockfile-selected packages in the built image. Pin the package resolution, retain usable package contents for regeneration, keep integrity-checked pristine references outside the workspace, and compare shipped artifacts against those references without network access at verification time.
- DrvFS can materialize tracked `120000` symlinks as ordinary executable files while also reporting every regular file as `755`. Set `core.filemode=false` only to suppress false executable noise, then compare index modes explicitly and restore every tracked symlink as a symlink; use symlink-preserving archive options and validate the extracted entry type.
- Integrity-check any embedded verifier-owned regression snapshot immediately after decoding and before execution. A malformed base64/gzip literal must be an infrastructure failure, never a silently weakened or syntactically different pass-to-pass guard.
- When a per-test verifier loop runs each graded test as `timeout N go test ...` under a freshly created empty GOCACHE, the first test pays the full cold compile of the vendored closure and every mid-loop vendored-file swap (probe/original) forces another rebuild. Signature: exactly the first one or two tests in execution order fail on the oracle while later tests asserting the same behavior pass. Fix the verifier, not the solution: add a bounded best-effort warm-up (`go test -run '^$'` per vendored variant, `|| true` so a non-compiling submission still grades FAILED rather than infrastructure_error), size `per_test_timeout_sec` for incremental compile+link, raise `[verifier] timeout_sec` (max 1800), and update any sha256 pin of `config.json` in lockstep.
- A verifier-owned dependency probe that replaces one vendored file is bypassable by a solver-added file in the same vendored package that re-exports the unexported builder. Normalize the probed package before the graded loop by deleting any file outside the known upstream inventory.
- A dependency-boundary requirement ("must not require X to generate Y") is only credibly graded when the check is visible inside `tests.patch`, not just in `test.sh` plumbing. Pattern: the verifier swaps in a panicking probe for the forbidden entry point; the test (1) calls that entry point itself under `recover` and `t.Fatal`s if it does NOT panic with the probe marker (fail-closed against running unarmed), then (2) runs the code under test through a recovering helper and turns a probe-marker panic into an explicit "still asked X to generate Y" failure. Field-value fingerprints (env, mounts) are evadable by overwriting and read as coverage_gap; do not rely on them for this requirement.
- Judge coverage findings can cite an earlier revision of `tests.patch` (e.g. an env-marker/linkname probe that was already replaced by the verifier-owned panic probe). Before changing anything, grep the current patch for the cited token; if absent, answer the finding with the current mechanism and its line refs instead of re-adding the old approach.

## Workspace-glob isolation and generated-code behavior

- A verifier-owned test path beneath a wildcard workspace member can break untouched-base manifest discovery before any selected test executes. Run genuine pass-to-pass coverage before injecting that member, or temporarily isolate the manifestless verifier path; require the final NOP report to contain every fail-to-pass ID as non-passing and every pass-to-pass ID as passing.
- Source-token assertions do not establish that generated JavaScript or TypeScript behaves correctly. Execute representative generated expressions in the actual pinned runtime, normalize non-JSON values such as `BigInt`, `Date`, and typed arrays, and grade nested collections, enum representations, and async helpers by observable results without requiring incidental renderer syntax.
- A trusting transform for an untagged sum has no safe discriminator unless the public contract supplies one. Specify its observable behavior explicitly, and do not smuggle forbidden runtime type/shape guards back into either the oracle or hidden tests.

## Python middleware and generated-build verification

- A nominal fail-to-pass count is not enough when the task form asks whether there are *more than* ten tests. Declare at least eleven independently attributable behavioral nodes, require at least one genuine untouched-base pass-to-pass node, disable extra-failure tolerance, and synthesize results from verifier-owned per-node exits rather than pytest console text.
- Generated-code tests must create a project that the public parser can really discover: include the ordinary module metadata and export bindings, invoke the public build command, compile the emitted module, and check observable registrations. Validate the fixture against the oracle before treating a build failure as a product defect.
- Do not pin generated Python to one formatter layout. Black and other formatters may wrap factory calls after the opening parenthesis; use whitespace-tolerant semantic matching or execute the generated artifact when possible.
- A no-argument middleware can still hide a provider precondition. Pair enabled tracing tests with disabled-provider transparency tests for every public hook, and verify that result identity, exception identity, and context restoration survive both normal and failing downstream calls.
